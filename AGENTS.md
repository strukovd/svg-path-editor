# SVG Path Editor

## О проекте

Это ранняя версия SVG-редактора на Vue 3, TypeScript и Pinia. Проект развивается давно и экспериментально, поэтому в нем одновременно встречаются актуальный код, временные решения, заготовки и legacy-код от более ранних подходов.

Основное направление развития — переход от редактора одного `path` к полноценной SVG-сцене с несколькими элементами, общими инструментами выделения и трансформации, импортом и последующим экспортом SVG.

Перед изменениями нужно изучить связанный код и проверить `DEVLOG.md`, `FEATURES.md` и `TODO.md`. Не следует считать каждый существующий подход окончательным или проводить большой несвязанный рефакторинг за один раз.

## Модель приложения

Архитектура строится как поэтапная композиция уровней:

```text
Приложение → Сцена → Элемент → внутреннее содержимое элемента
```

Каждый следующий уровень отвечает только за свою модель и поведение. Наличие отдельного архитектурного уровня не означает обязательное наличие отдельного Pinia store для него.

### Оболочка приложения

`AppStore` хранит глобальное состояние оболочки приложения: панели, footer, меню и другие части layout. Панели представлены списками описаний и загружаются как динамические компоненты. В дальнейшем пользователь сможет управлять составом и расположением панелей.

### Сцена

Сцена — непосредственно SVG-редактор. Ее общедоступное состояние находится в `SceneStore`:

- размеры сцены и состояние камеры;
- SVG-элементы;
- выделение и редактируемый элемент;
- активный инструмент и режим взаимодействия;
- настройки сцены;
- поля состояния истории.

Термины `selected`, `active`, `editable`, `mode` и `tool` пока не образуют окончательную модель. Не закреплять их текущую связь новой логикой без отдельного обсуждения. В частности, возможен переход к более явным полям вроде `activeElementId` и `activeTool`.

### Элементы сцены

SVG-примитивы должны постепенно становиться обычными элементами единой модели сцены. Это относится и к reference image: текущая отдельная реализация `SceneReferenceImage` временная, в дальнейшем изображение должно стать обычным SVG-элементом `image` в `SceneStore`, чтобы использовать общее выделение, трансформации и историю.

Сцена владеет коллекцией элементов, поэтому сами данные элементов могут оставаться в `SceneStore.elements`. Отдельный singleton `ElementStore` не требуется только ради симметрии с `AppStore` и `SceneStore`: элементов много, и единый store не должен дублировать коллекцию сцены или состояние активного элемента.

Уровень Element отвечает за отрисовку и свойства конкретного SVG-элемента. `ElementComponent` уже выделен из цепочки `v-if`/`v-else-if` в `SceneComponent` и является началом этого уровня. Политика выбора элемента принадлежит сцене; в дальнейшем элемент можно отвязать от прямого знания о `SceneStore`, передавая ему состояние через props и получая намерения через emits.

`SceneEntityBox` — суррогатный wrapper/overlay, который находится рядом с SVG-элементом, а не является его DOM-родителем. Он отображает рамку активного элемента и предоставляет управление выделением и трансформациями. Его текущая реализация еще требует изучения и не считается окончательной.

### Режим редактирования элемента

`mode` задуман как контекст взаимодействия, а не просто как название выбранного инструмента. В обычном режиме пользователь работает со сценой и целыми элементами: выбирает, перемещает, масштабирует и вращает их. В режиме редактирования фокус изолируется на одном элементе, а внешний мир временно скрывается, блокируется или замораживается.

Для `path` этот режим должен предоставлять работу с его внутренней структурой: точками, сегментами и направляющими. Перемещение целого элемента и перемещение точки — разные операции разных уровней, их не нужно объединять только из-за внешнего сходства жестов.

Предпочтительно сохранять общий режим `edit`, а конкретный редактор определять по типу элемента, указанного через `editableId`. Это позволит позже использовать тот же переход для `text`, `polygon`, групп и других элементов со своей внутренней моделью.

## Разделение состояния и логики

Принята следующая практическая граница ответственности:

- Pinia stores хранят общедоступное реактивное состояние. Оно должно быть доступно компонентам из разных частей приложения как единый экземпляр.
- Composables содержат декомпозированную логику отдельных возможностей сцены: history, zoom, camera movement, grid, selection, transformations и другие фичи.
- Vue-компоненты отвечают за UI, связывание фич с шаблоном и локальное состояние, которое точно не требуется снаружи.
- Краткоживущее состояние DOM-взаимодействия, например текущий drag, ссылка на SVG, `ResizeObserver` или координаты начала жеста, не нужно автоматически переносить в Pinia. Оно может оставаться локальным либо находиться в composable с корректным lifecycle.

Не возвращать всю логику обратно в `SceneStore` только ради глобального доступа. Одновременно не создавать singleton-composable без необходимости: если фиче нужен единый экземпляр или общий доступ, это должно быть явно обеспечено точкой композиции, store либо другим согласованным механизмом.

## История изменений

История вынесена в `useSceneHistory`, но пока не подключена к остальной сцене. Это осознанно незавершенный рефакторинг.

На текущем этапе историю нужно отложить и убрать старые вызовы `sceneStore.pushHistory`, мешающие работе редактора. Сам composable истории и поля истории в `SceneStore` следует сохранить до следующего отдельного этапа.

Пока не решено окончательно:

- какие данные входят в `SceneSnapshot`;
- нужно ли сохранять выделение, режим и активный инструмент вместе с документом;
- как включать и отключать запись истории;
- где находится точка композиции экземпляра истории.

Для межмодульных связей выбран концепт отдельного глобального `useManagerStore`. Его назначение — не хранение данных сцены, а роль центрального посредника/IoC-хаба, который знает связи между независимыми модулями и доставляет им события. Предполагаемый вызов со стороны фичи может выглядеть как `manager.pushHistory(data)`. `useManagerStore` пока не реализовывать: история отложена, а интерфейс менеджера нужно определять по мере появления реальных связей, не наполняя его заранее предполагаемыми методами.

Не импортировать `useSceneHistory` внутрь `SceneStore`: текущий composable уже зависит от стора, поэтому обратный импорт создаст неверное направление зависимости, потенциальный цикл и смешение ответственности. Сам по себе composable не обязан зависеть от lifecycle компонента или владеть отдельным состоянием; точку его создания и время жизни нужно выбирать по фактическим зависимостям. Не заменять выбранный `useManagerStore` неявными `$subscribe` или `$onAction` без отдельного решения.

При будущем подключении истории учитывать границы пользовательской операции: например, drag может обновлять элемент на каждом `mousemove`, но создавать один snapshot только после завершения жеста.

## Текущие временные решения

- `useSceneDemoSeeds` вынесен и временно подключен в `SceneComponent` для заполнения ранней сцены примерами.
- Проверка в `ensureInitialized` исторически была связана с добавлением demo-элементов и может быть пересмотрена.
- `SceneReferenceImage` пока хранит изображения локально, но должен быть заменен общей моделью элемента `image`.
- Логика selection/editing требует отдельного проектирования.
- Singleton-state и watcher в `useSceneGrid` требуют проверки перед дальнейшим развитием.
- Наблюдение за изменением размеров сцены вынесено в `useSceneCalibrator`; composable владеет `ResizeObserver` и освобождает его на unmount. Первичная инициализация размеров остается локально в `SceneComponent`, потому что снаружи компонента она не нужна.
- Заготовки composables элементов пока могут быть пустыми; не считать их завершенными реализациями.

## Ближайший технический фокус

1. Разобрать `useSceneGrid` и устранить два источника истины для состояния сетки.
2. Отдельно спроектировать понятную модель selection/active/editing/tool/mode.
3. Продолжить постепенную декомпозицию `SceneStore` по feature-composables.
4. Сделать `image`, включая reference image, обычным элементом сцены.
5. Вернуться к контракту истории после стабилизации основных операций сцены.

# Стиль кода проекта

## Vue-компоненты
- Не использовать `scoped` стили в `.vue` компонентах.
- Не использовать BEM-нейминг для локальной разметки компонентов.
- Держать стили компонента в том же `.vue` файле, если нет явной причины вынести их отдельно.
- Использовать короткие структурные классы, совпадающие с шаблоном компонента.

## Структура SCSS
- Использовать вложенность SCSS.
- Иерархия стилей должна повторять HTML-иерархию.
- Если шаблон выглядит так:

```html
<div class="wrapper">
	<div class="content">
		<span class="message"></span>
	</div>
</div>
```

то SCSS должен выглядеть так:

```scss
.wrapper {
	.content {
		.message {
		}
	}
}
```

- Не сплющивать вложенную структуру компонента в селекторы вида `.wrapper-content-message`.
- Использовать `&` только для классов состояния и псевдоселекторов, например `&.active`, `&:hover`, `&:focus-visible`.

## Оформление
- По возможности использовать существующие SCSS-переменные из `src/styles/main.scss`.
- UI редактора должен быть компактным и утилитарным.
- Не делать несвязанный визуальный редизайн при изменении поведения компонента.
