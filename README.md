# ⚙️ Концепция проекта
Концепция нужна что бы не путаться и интуитивно понимать что где искать.

Приложение делится на иерархию модулей (домены).
Глянем сразу (модулей не много):
```
App (Главная страница, знает о своих: menu, toolbar, scene, sidebar, footer)
└── Scene (Центральная часть экрана, основная сцена, знает о элементах на сцене, какие выбраны, какой редактируется, ..)
    └── Element (SVG-element, знает свойства элемента, типа: цвет,прозрачность, .., знает как рисовать и редактировать каждый вид элементов )
```

Иерархия кажется понятной и логичной, и кажется что если нужен - масштаб сцены,
то его нужно искать в КОМПОНЕНТЕ сцены..
НО! не торопитесь искать его там.

Если бы я всё хранил в компоненте, компонент бы стал свалкой, в которой невозможно было бы разобраться.

Поэтому - понятие модуля делится на сущности:
```
┌────────────────────────┐
│ 						 │
│ 🟩 компонент (vue),	 │
│ 🟨 стор (pinia),		 │
│ 🟪 композаблы.		 │
│ 						 │
└────────────────────────┘
```

А теперь подробнее..

### Зачем это нужно?
- Компонент не сможет хранить все данные\состояния и методы в себе:<br>
1. Во первых, это сложно читается, код компонента превращается в свалку<br>
╰┈> декомпозируем логику блоками, выносим в composables.<br>
`То есть мы осуществляем вынос методов «за контур» компонента, с сохранением доступа и владения в контексте одного модуля.`
<br><br>
1. Нужен порядок\иерархия для логики, что бы сразу было понятно, кто за что отвечает.<br>
╰┈> Делим на модули<br><br>
1. Большинству других компонентов (виджетов) в проекте, нужно знать внешние значения (например модулю настроек)
2. Компонент работает экземплярами, а что бы хранить доступное значение нужен singleton (единый экземпляр)<br>
╰┈> Выносим такие значения в Pinia, которая даст singleton (единый экземпляр) и привычное использование<br><br>

❗ ИТОГО, складываются правила:
- Все общедоступные поля модуля храним в его `🟨 store` для глобальной доступности (singleton) и полной карты состояния в одном месте
- Методы, вычисления и реакции на изменение состояния храним в тематических `🟪 composable`, чтобы декомпозировать логику модуля
- «Живое» поле, значение которого автоматически поддерживает фоновый обработчик или mutator-composable, помечаем суффиксом `_`, например `context_` или `cursor_`. Такое поле доступно остальному приложению для чтения, но изменять его напрямую должен только назначенный владелец
- Mutator-composable называем по схеме `useMutator<Домен><Назначение>`, например `useMutatorSceneContext`
- Mutator с `watchEffect`, глобальным обработчиком или таймером запускается ровно один раз родительским компонентом своего домена. Для сцены таким владельцем является `SceneComponent`
- `🟩 Компонент` может содержать поля и методы, но только если они небольшие, и точно не нужны снаружи (другим компонентам)

«Живым» считается не просто изменяемое поле, а поле с одним автоматическим владельцем: он обновляет значение по событиям или на основе другого состояния, а остальные части приложения его только читают. Поэтому `context_` является живым полем, вычисляемым из `selectedIds` и `editableId`, а `cursor_` — живым полем, координаты которого обработчик мыши переводит через `clientToWorld`. Суффикс `_` — только архитектурная памятка, а не механизм ограничения доступа TypeScript. Символ `$` для этой метки не используем, поскольку он уже принят в служебном API Vue и Pinia (`$state`, `$patch`, `$reset`, `$subscribe`).


## Точка входа
Точка входа сцены — [SceneComponent.vue](/src/components/common/scene/SceneComponent.vue). Компонент получает исходное состояние из `SceneStore`, подключает нужные scene-composables и рисует элементы из `sceneStore.elements` через `ElementComponent`.

Текущая цепочка выглядит так:

```text
SceneComponent
├── SceneStore — полная карта общедоступного состояния
├── useScene* — операции отдельных возможностей сцены
├── useMutatorScene* — автоматическое обновление служебных полей SceneStore
└── ElementComponent — отрисовка каждого SVG-элемента
```
